# Leon AI V2.0 产品与技术计划

> 文档状态：设计与代码审计

> 日期：2026-07-30

## 1. V2.0 产品定位

- 品牌：Leon AI
- 中文名称：AI商务邮件工作台
- 英文名称：AI Business Email Workspace
- 版本标识：V2.0 Development

V2.0 将产品从“输入一段需求后生成或优化邮件”升级为“围绕商务邮件完整任务组织的工作台”。用户无需掌握 Prompt，也不必事先准备完整草稿，只需选择任务、填写必要事实，或粘贴收到的邮件，即可完成：

1. 写一封新邮件；
2. 回复收到的邮件；
3. 优化已有草稿；
4. 发送前检查。

产品仍坚持以下边界：

- 不自动发送邮件；
- 不在 V2.0 首期增加用户注册、支付、数据库或历史记录；
- 不保存用户输入和结果；
- 风险、本地化及发送前检查均为辅助提示；
- 用户发送前必须核对姓名、日期、金额、责任、承诺和敏感信息。

## 2. 为什么需要 Leon AI V2.0

### 2.1 为什么不直接使用豆包、ChatGPT 或 DeepSeek

豆包、ChatGPT、DeepSeek 等通用聊天 AI 已经可以完成翻译、润色和邮件生成，Leon AI 不应宣称底层模型一定更强。真正的差别在于产品是否把模型能力组织成普通员工可以直接完成工作的流程。

使用通用聊天 AI 时，用户通常需要：

1. 先判断自己应该提出什么任务；
2. 自行组织 Prompt；
3. 判断还需要提供哪些业务事实；
4. 多轮补充遗漏信息；
5. 自行检查 AI 是否遗漏问题或擅自承诺；
6. 从对话内容中复制、整理和再次修改最终邮件。

这对于熟悉 Prompt 和英文商务沟通的人并不困难，但对大量普通员工而言，真正的成本不是“找不到 AI”，而是“不知道怎样把业务任务完整、稳妥地交给 AI”。

Leon AI V2.0 不替代通用 AI，而是在通用模型之上提供任务入口、必要事实收集、结构化分析、风险提示、覆盖检查和可直接审核的邮件结果。

### 2.2 与通用聊天 AI 的核心区别

> **通用 AI：**用户需要自己理解任务、组织 Prompt、补充信息、检查遗漏并复制结果。  
> **Leon AI：**用户选择业务场景，系统主动询问必要事实、分析对方诉求、识别遗漏和风险，并生成可直接审核使用的完整商务邮件。

| 对比维度 | 通用聊天 AI | Leon AI V2.0 |
| --- | --- | --- |
| 入口 | 开放式对话框 | 明确的业务任务和场景 |
| 信息收集 | 用户自己决定说什么 | 系统按场景询问必要事实 |
| 回复邮件 | 依赖用户自己写 Prompt | 先提取来信诉求，再逐项收集立场 |
| 完整性 | 用户自行判断有无遗漏 | 检查问题覆盖、行动、期限和附件 |
| 风险 | 依赖用户主动要求检查 | 工作流内置敏感信息和承诺提示 |
| 输出 | 一段聊天回答 | 可编辑、可复制、可导出的邮件草稿 |
| 控制 | 容易在多轮对话中混入推测 | 数据结构明确区分原始事实、AI分析和用户决定 |

### 2.3 V2.0 解决的不是翻译问题

翻译只解决“这句话英文怎么说”。商务邮件工作真正需要解决的是：

- 这封邮件的目的是什么；
- 应该提供哪些背景；
- 对方需要采取什么行动；
- 是否给出了明确期限；
- 收到的邮件提出了几个问题；
- 用户对每个问题是什么立场；
- 是否遗漏附件、金额、责任或承诺；
- 语气是否与关系和场景匹配；
- 是否含有不适合提交给第三方 AI 的内容；
- 最终邮件是否可以由用户快速核对后使用。

因此 V2.0 的核心是**商务任务结构化、立场控制和完成度检查**，英文表达是其中一个必要结果。

### 2.4 为什么场景化工作流更适合普通员工

开放式 Prompt 把任务设计责任交给用户。场景化工作流则把常见业务经验转化为少量、明确、可验证的问题，例如催交期只需要询问原定日期、当前状态、新截止日期、延迟影响和期望行动。

场景化设计的优势：

- 用户看到字段即可理解需要准备什么；
- 必填项可以在调用 AI 前验证；
- 不同部门使用一致的任务语言；
- AI 更容易区分事实与希望采用的表达；
- 可对场景配置做自动化测试；
- 高风险字段可以获得更有针对性的提醒；
- 用户无需反复学习 Prompt 模板。

场景化不等于限制用户。每个场景应保留“补充说明”和“高级选项”，无法归类的任务仍可进入通用写邮件流程。

### 2.5 为什么回复邮件更有日常价值

很多职场人员每天面对的主要任务不是从零写邮件，而是处理别人已经发来的邮件。回复比新写邮件更复杂，因为用户必须同时理解对方的多个诉求、期限和隐含责任，并决定哪些内容可以接受、拒绝或暂时无法确认。

“回复收到的邮件”能带来的直接价值包括：

- 减少阅读长英文邮件的理解成本；
- 把多个问题拆成可逐项处理的清单；
- 防止只回答最后一个问题而遗漏前文；
- 避免 AI 在用户未表态时自行同意期限或责任；
- 把“理解来信”和“组织英文回复”合并为一条可检查的工作流。

这使回复功能比单纯的文字生成更贴近日常工作频率，也更能体现 Leon AI 与普通翻译工具的差异。

## 3. 核心用户价值

### 3.1 少思考

用户不需要学习 Prompt，也不需要先构思完整邮件结构。系统通过“今天需要完成什么？”和场景问题把任务拆解成容易回答的事实。

### 3.2 少输入

系统只询问当前任务真正需要的信息。常用发件人信息在当前 Session 内共享；已经从来信中可靠提取的信息不重复要求用户填写。

### 3.3 少遗漏

系统检查行动要求、截止日期、来信中的问题、附件、金额、责任、承诺和敏感信息，并明确显示仍未回答或需要人工核对的事项。

### 3.4 更容易完成工作

最终结果不是逐句翻译，而是目的、背景、立场和下一步清楚的完整商务邮件。用户可以直接编辑、复制或导出，并在人工审核后发送。

### 3.5 V1.0 与 V2.0 用户流程对比

```text
V1.0
用户组织需求
    ↓
填写大段文字
    ↓
AI 生成或优化
    ↓
用户自行检查是否遗漏
```

```text
V2.0
选择任务
    ↓
系统询问必要事实
    ↓
AI 整理与分析
    ↓
生成邮件
    ↓
发送前检查
    ↓
用户确认
```

V2.0 不是增加更多表单，而是把原来由用户自行承担的任务拆解、遗漏检查和结果整理变成产品默认流程。

## 4. 目标用户画像

### 4.1 Persona A：项目工程师

- **常见邮件任务**：技术澄清、文件提交、图纸审批催办、设备问题说明、会议行动项确认。
- **当前困难**：掌握技术事实，但难以把背景、问题、影响和所需行动组织成简洁英文。
- **使用通用 AI 的问题**：容易粘贴大量技术内容，却未明确对方必须回答的问题；模型也可能改动技术含义。
- **Leon AI 价值**：通过场景字段区分已知事实、待确认问题、引用编号、截止时间和附件，发送前检查是否遗漏行动要求。
- **最适合首批场景**：技术澄清请求、文件审批催办、会议行动项确认、风险升级。

### 4.2 Persona B：采购人员

- **常见邮件任务**：催报价、催交期、确认 PO、要求供应商解释延期、要求更新计划。
- **当前困难**：知道业务事实，但不清楚如何组织英文表达、控制语气并明确延迟影响。
- **使用通用 AI 的问题**：需要自行写 Prompt，容易遗漏原定日期、新期限、影响和具体行动要求。
- **Leon AI 价值**：通过固定场景主动询问原定日期、新截止日期、延迟影响及要求供应商采取的行动，并提示价格、付款和承诺风险。
- **最适合首批场景**：催报价、催交期、供应商延期解释、更新计划、PO 确认。

### 4.3 Persona C：行政人员

- **常见邮件任务**：会议邀请、行程确认、客户来访安排、场地或时间变更、内部审批请求。
- **当前困难**：需要频繁处理时间、地点、时区、参会人和附件，任何遗漏都会造成重复沟通。
- **使用通用 AI 的问题**：生成语言通常没有问题，但仍需人工检查会议时间、地址、联系人和确认事项。
- **Leon AI 价值**：用结构化字段收集安排信息，自动检查关键时间、时区、地点和对方需要确认的事项。
- **最适合首批场景**：会议邀请、通知安排变更、客户来访确认、请求审批。

### 4.4 Persona D：HR 人员

- **常见邮件任务**：面试安排、候选人资料请求、入职文件提醒、培训通知、内部政策沟通。
- **当前困难**：需要兼顾礼貌、清晰、隐私和一致性，涉及个人信息时风险更高。
- **使用通用 AI 的问题**：用户可能直接粘贴候选人隐私信息，模型也无法知道公司内部政策和授权边界。
- **Leon AI 价值**：在提交前提示个人敏感信息，只询问邮件必要事实，并检查日期、文件清单和候选人需要完成的行动。
- **最适合首批场景**：会议邀请可覆盖面试安排；资料请求可覆盖入职文件提醒。专门的录用、薪酬和纪律场景不进入首发。

### 4.5 Persona E：项目经理或部门经理

- **常见邮件任务**：项目进展汇报、风险升级、资源或预算审批、跨部门协调、客户问题回复。
- **当前困难**：需要快速从大量信息中提炼结论、影响、决策事项和责任人，同时避免过度承诺。
- **使用通用 AI 的问题**：长 Prompt 编写成本高，生成结果可能保留过多背景，或擅自把建议写成管理承诺。
- **Leon AI 价值**：以高管简洁结构组织现状、影响、需要决策和下一步，并检查承诺、责任和未确认事项。
- **最适合首批场景**：项目进展汇报、风险升级、请求审批、回复客户邮件。

## 5. V1.0 现状分析

### 5.1 当前模块职责

| 文件 | 当前职责 | 评价 |
| --- | --- | --- |
| `app.py` | 页面样式、访问门禁、导航、表单、Session State、风险检查编排、AI 调用、结果编辑、复制、案例和服务状态 | 功能完整，但 1459 行，职责过多，是 V2.0 的主要重构点 |
| `ai_service.py` | DeepSeek 客户端、异常映射、JSON 解析、一次修复、纯文本降级、签名拼接、生成和优化入口 | 基础设施可复用，但返回模型与邮件业务耦合，需要支持多种任务类型 |
| `prompts.py` | 生成、优化、格式修复 Prompt 和语气规则 | 可复用语气与事实约束；V2.0 应按工作流拆分 Prompt，而不是继续扩充单文件 |
| `config.py` | DeepSeek、输入长度、产品名称和版本配置 | 可复用；V2.0 需要把产品元数据与 AI 配置继续集中管理 |
| `content_risk_service.py` | 本地敏感凭证、个人信息、机密、价格、法律责任和承诺检查 | 可直接作为所有四个入口的前置检查基础 |
| `localization_service.py` | 国家或地区、称谓、礼貌程度和跨文化提示 | 可复用；需扩展输入模型，使其接受提取后的收件人信息 |
| `communication_analysis_service.py` | 沟通质量分析数据模型和容错解析 | 可演进为发送前检查模型的一部分 |
| `examples.py` | V1.0 案例数据 | 数据驱动方式可复用；V2.0 应升级为场景定义数据 |
| `access_control.py` | 可选测试访问码及安全环境标签 | 保持独立并复用，不把它当作正式身份认证 |
| `tests/` | 服务单元测试与 Streamlit AppTest | 测试基础良好，但 V2.0 需要按工作流增加契约、状态迁移和端到端测试 |

### 5.2 当前页面与状态

当前页面只有“写英文邮件”和“优化英文邮件”两个模式。表单、风险提示、本地化建议、AI 调用和结果区分别在两个大分支中重复编排。

`SESSION_DEFAULTS` 集中初始化状态，但当前状态存在以下特点：

- 键名按 `generate_*`、`improve_*` 和 `shared_*` 平铺；
- 页面切换依赖 `PAGE_WIDGETS`、`preserve_page_inputs()` 和 `restore_page_inputs()`；
- 生成结果、编辑结果、分析结果分别维护多个相近键；
- `request_in_progress` 是全局布尔值，无法表达“分析原邮件”“生成回复”“发送前检查”等不同任务；
- 高风险确认通过输入摘要绑定，这一机制设计正确，可以复用；
- 结果只存在于当前 Session State，没有数据库持久化，符合现阶段隐私边界。

四个工作流加入后，继续增加平铺键会显著提高组件 key 冲突、错误复用结果和切换页面丢状态的风险。

### 5.3 当前 AI 输出与解析

V1.0 使用一个共享 JSON 结构：

```json
{
  "subject": "",
  "body": "",
  "communication_analysis": {
    "purpose": "",
    "action_required": "",
    "deadline": "",
    "tone": "",
    "commitment_risk": "",
    "ambiguity_risk": "",
    "localization_note": "",
    "improvement_suggestions": []
  }
}
```

解析链路为：

1. 请求 JSON mode；
2. 严格解析；
3. 最多一次格式修复请求；
4. 如第一响应可识别为普通邮件，则降级显示主题和正文；
5. 否则返回安全的中文错误。

该链路适合继续作为底层解析框架，但 V2.0 不应让“原始邮件分析”“回复生成”和“发送前检查”勉强共用 `EmailResult`。应为不同任务建立独立模型和解析器，并共用同一套请求、错误映射、代码块清理和一次修复策略。

### 5.4 当前测试结构

现有测试覆盖：

- 访问码与运行环境；
- DeepSeek 请求参数、签名、语气、异常和 JSON 降级；
- 必填项、长度、重复请求、Session State、案例填充和高风险确认；
- 内容风险、本地化和沟通分析服务。

主要缺口：

- 没有独立的 Prompt 契约测试；
- 没有工作流状态迁移测试；
- 没有“原邮件分析 → 用户立场 → 回复结果”的多步骤测试；
- 没有场景定义完整性测试；
- 没有导出内容和 `.eml` 格式测试；
- `AppTest` 目前依赖大页面中控件顺序，V2.0 应更多使用稳定且唯一的 key。

## 6. 用户反馈及问题定义

以下问题来自本次产品目标和当前工作流审计，并非已量化的用户行为数据：

1. **输入门槛仍然偏高**：用户要自行组织“中文需求”，仍可能不知道该提供哪些事实。
2. **回复邮件没有完整流程**：当前只能把收到的邮件当作待优化文本，无法先提取对方诉求，再让用户逐项确定立场。
3. **检查能力依附于生成结果**：用户已有可发送邮件时，不能独立进行发送前检查。
4. **页面按技术能力组织，而不是按用户任务组织**：用户需要先理解“生成/优化”，而不是直接选择“我要写、回、改、查”。
5. **状态结构无法平滑扩展**：两个页面尚可管理，四个多步骤流程继续使用平铺状态会变得脆弱。
6. **AI 数据结构过于单一**：`EmailResult` 无法自然表达原邮件诉求、待回复问题和分级检查项。

V2.0 的核心问题定义是：降低商务邮件任务的准备成本，同时确保多步骤流程中的事实、用户立场和风险确认不会被 AI 或页面重跑意外改变。

## 7. V2.0 四个核心用户流程

四条流程都遵守以下体验原则：

- 普通场景以 60 秒内完成为目标；
- 原则上不超过 3 个主要操作步骤；
- 已经提供或可靠提取的信息不重复填写；
- 首屏只显示必需字段；
- 地区、签名、补充背景等放入“高级选项”；
- AI 只由明确按钮触发；
- 系统不自动发送邮件。

### 7.1 A：场景化写新邮件

**建议主要步骤：3 步**

#### 步骤 1：选择场景

- **用户入口**：首页高频场景卡片，或“更多场景”分类列表。
- **页面展示**：场景名称、适用说明、预计填写时间和“更换场景”。
- **用户填写**：不填写内容，只选择最接近的任务。
- **AI 后台工作**：无 AI 调用。
- **风险检查**：不触发。

#### 步骤 2：填写必要事实

- **页面展示**：最多 4 至 6 个核心字段，每个字段使用业务语言而非 Prompt 术语。
- **用户填写**：例如对象、当前事实、要求的行动、截止时间和影响。
- **高级选项**：收件人地区、语气、主题偏好、发件人签名和补充说明。
- **AI 后台工作**：无调用；本地校验必填项并整理场景数据。
- **风险检查**：用户输入时进行本地检查；高风险内容必须确认后才能生成。

#### 步骤 3：生成、检查与完成

- **AI 后台工作**：基于场景结构和用户事实生成主题、正文和简洁分析，不补充未提供事实。
- **系统输出**：可编辑主题、正文、遗漏提醒、本地化提示和发送前检查摘要。
- **用户修改**：直接编辑主题和正文；如修改关键事实，检查结果标记为需要重新检查。
- **最终操作**：复制主题、复制正文、复制完整邮件、可选导出；不自动发送。
- **异常降级**：AI 失败时保留全部输入并显示安全错误；格式异常但可识别邮件时显示正文并标记分析不可用；不清空表单。

### 7.2 B：回复收到的邮件

**建议主要步骤：3 步。**这是 V2.0 的核心工作流，详细机制见第 9 节。

#### 步骤 1：粘贴并分析来信

- **用户入口**：首页独立突出卡片“回复收到的邮件”，不放入“更多场景”。
- **页面展示**：原邮件输入框、隐私提醒、长度说明和“分析来信”按钮。
- **用户填写**：粘贴收到的邮件；主题可选。
- **AI 后台工作**：提取对方目的、要求、问题、日期、金额、责任、紧急程度和可识别的邮件主题。
- **风险检查**：粘贴后先在本地触发；高风险内容确认前不发送给 AI。
- **系统输出**：结构化来信摘要，而不是立即生成回复。

#### 步骤 2：确认立场和缺失事实

- **页面展示**：按问题逐项显示对方要求，以及“接受 / 部分接受 / 拒绝 / 请求更多信息 / 暂时无法确认 / 自定义”。
- **用户填写**：每个需要回复的事项选择立场；只对缺少的必要信息显示追问。
- **AI 后台工作**：无自动调用；系统将用户选择转为明确的 `ReplyDecision`。
- **风险检查**：对用户新增的金额、期限、承诺和责任再次进行本地检查。
- **系统输出**：生成前确认摘要，包括已决定和仍未决定的事项。

#### 步骤 3：生成、覆盖检查与完成

- **AI 后台工作**：只依据原邮件事实和用户立场生成回复；同时返回逐项覆盖结果。
- **系统输出**：完整回复、已覆盖事项、仍未回答的问题、承诺提醒和发送前提示。
- **用户修改**：直接编辑主题和正文；未回答事项始终保留在结果旁。
- **最终操作**：复制或导出，不自动发送。
- **异常降级**：来信分析失败时不猜测问题；允许用户重试或转到“写新邮件”。回复生成失败时保留分析和用户立场，用户无需重新填写。

### 7.3 C：优化已有草稿

**建议主要步骤：2 步**

#### 步骤 1：粘贴草稿并选择目标

- **用户入口**：首页“优化已有草稿”。
- **页面展示**：主题、正文、目标语气，以及可折叠的地区和签名。
- **用户填写**：粘贴草稿；选择“更正式 / 更友好 / 更明确 / 更简洁”。
- **AI 后台工作**：此时不调用。
- **风险检查**：输入后立即执行本地检查，高风险需确认。

#### 步骤 2：优化、对比与完成

- **AI 后台工作**：保留事实、立场、日期、金额、编号和承诺，改善结构、语法、语气和行动要求。
- **系统输出**：优化后的主题和正文、主要改进、仍需确认的内容。
- **用户修改**：直接编辑结果；可切换查看原文，但不要求逐项接受修改。
- **最终操作**：复制或导出，不自动发送。
- **异常降级**：AI 失败时保留原草稿；无法返回完整分析但有可识别邮件时显示优化结果并提示人工对比。

### 7.4 D：发送前检查

**建议主要步骤：2 步**

#### 步骤 1：粘贴最终邮件

- **用户入口**：首页“发送前检查”，也可从其他三个结果页携带当前编辑内容进入。
- **页面展示**：主题和正文；从结果页进入时自动带入，但允许修改。
- **用户填写**：只需补充缺失的主题或正文。
- **AI 后台工作**：不自动调用。
- **风险检查**：立即执行本地敏感信息、称谓和基础结构检查。

#### 步骤 2：检查、修正与完成

- **AI 后台工作**：检查目的、行动要求、期限、附件提及、承诺、责任、语气、歧义、称谓和必要背景。
- **系统输出**：按“需要修改 / 建议检查 / 良好”列出检查项，不提供安全百分比。
- **用户修改**：在同页编辑邮件；修改后旧报告显示“内容已改变，请重新检查”。
- **最终操作**：完成检查后复制或导出；用户自行在邮箱中发送。
- **异常降级**：AI 检查失败时仍显示本地风险检查结果，并明确语义检查未完成。

## 8. 首页与页面信息架构

### 8.1 首页设计原则

首页不从“生成、分析、优化”等技术能力出发，而是回答普通员工的直接问题：**今天需要完成什么？**

“回复收到的邮件”必须与高频新邮件场景同级突出，因为它使用频率高、价值差异明显，不能隐藏在“更多场景”中。

### 8.2 首页文字线框图


### 8.3 桌面端布局

- 页面内容宽度保持集中，不使用复杂仪表盘。
- “回复收到的邮件”和“催供应商”占第一排两张较大的主卡片。
- 第二排展示四个高频场景，每行两张。
- “优化已有草稿”“发送前检查”“更多场景”使用次级按钮或紧凑卡片。
- 场景卡只显示名称和一句价值说明，不显示所有字段。
- 首页不显示完整功能介绍长文，详细说明放入折叠区。

### 8.4 手机端布局

- 所有入口改为单列。
- “回复收到的邮件”固定为第一张主卡。
- 首屏最多显示回复入口和三个高频场景，其他场景通过“查看更多”展开。
- 卡片整行可点击，触控高度不低于 44px。
- 不使用需要横向滚动的导航或四列卡片。
- 工作流顶部提供简短“返回工作台”，不占用固定悬浮空间。

### 8.5 场景分类

场景按用户任务而非 AI 能力分类：

- **回复邮件**：独立主入口；
- **采购与供应商**：催报价、催交期、计划更新、延期解释、PO 确认；
- **项目与工程**：进展汇报、风险升级、审批催办、技术澄清、行动项确认；
- **行政与管理**：会议邀请、审批请求、安排变更、客户来访；
- **处理现有内容**：优化草稿、发送前检查。

分类只用于发现入口，不改变底层工作流；大部分场景最终进入“写新邮件”。

### 8.6 避免首页按钮过多

- 首页直接展示 6 个高频入口，其中“回复邮件”始终固定。
- “优化草稿”和“发送前检查”作为两个稳定工具入口。
- 其余场景进入“更多场景”，按分类折叠或搜索。
- 不为每种语气、部门或国家创建首页按钮。
- 根据外部测试数据调整首页高频场景，首发不做个性化推荐。

### 8.7 返回首页和切换任务

- 工作流顶部显示 `← 返回工作台`。
- 同一区域显示当前任务名称和“更换场景”。
- 返回首页不清空当前 Session 中的工作流输入。
- 用户切换任务时，如当前有未复制或未确认的编辑结果，显示非阻断提示：“当前内容会在本次会话中保留。”
- 提供“清空当前任务”，但不影响共享签名和其他任务。

### 8.8 工作流页面统一骨架

每个入口保持一致的阅读顺序：

1. 当前任务、步骤和返回入口；
2. 当前步骤必要输入；
3. “高级选项”中的语气、地区和签名；
4. 本地风险提示及确认；
5. 唯一主操作按钮；
6. 分析或邮件结果；
7. 编辑、检查、复制和导出；
8. 辅助说明。

移动端使用单列；桌面端也保持主流程单列，只把摘要或检查项作为辅助卡片，避免输入与结果争夺注意力。

## 9. “回复收到的邮件”详细设计

### 9.1 信息提取与多个问题识别

系统先把原邮件转换为结构化分析，不立即写回复。每个待回复事项包含：

- 稳定的 `item_id`；
- 对方原意的简洁转述；
- 事项类型：请求、问题、期限、信息通知或责任主张；
- 是否必须回复；
- 对应日期、金额、编号或附件；
- 提取证据位置的简短提示，但不在日志中保存原文；
- 不确定标记。

AI 应按语义拆分，而不是只按问号拆分。例如“请确认交期，并说明延期原因及补救计划”至少包含三个待回复事项。页面用编号清单展示，用户可合并误拆项或标记“这项无需回复”，但首发不提供复杂的自由拖拽编辑。

### 9.2 用户立场控制

每个必须回复的问题都要求用户选择：

- 接受；
- 部分接受；
- 拒绝；
- 请求更多信息；
- 暂时无法确认；
- 自定义。

选择立场后只显示必要的补充字段：

- **接受**：确认的事实、日期或行动；
- **部分接受**：接受部分、不能接受部分和替代方案；
- **拒绝**：可公开说明的原因及下一步；
- **请求更多信息**：需要对方补充的具体信息；
- **暂时无法确认**：预计何时或在什么条件下可以回复；
- **自定义**：用户自己的处理说明。

系统不得把“未选择”解释为接受，也不得为了让邮件完整而自动补充承诺。

### 9.3 防止 AI 擅自承诺

采用四层控制：

1. **数据层**：用户决定与 AI 提取结果分开保存，生成服务只接收已确认的 `ReplyDecision`。
2. **Prompt 层**：明确禁止增加日期、金额、责任、保证、同意或拒绝立场。
3. **输出层**：返回逐项 `coverage`，标记每项使用了哪种用户立场。
4. **检查层**：本地关键词和 AI 检查共同标记新增的保证、确定性期限、赔偿、责任接受和付款承诺。

如果生成结果出现用户未提供的明确承诺，状态必须为“需要修改”，不能以普通建议弱化。

### 9.4 用户没有足够信息时

“暂时无法确认”和“请求更多信息”是正式有效的处理立场，不是错误状态。系统可以生成：

- 告知对方正在内部核实；
- 明确当前无法确认的具体事项；
- 询问所需补充资料；
- 仅在用户提供时说明预计回复时间；
- 避免编造内部审批进度。

如果某个关键事项没有任何立场，允许生成回复前显示“仍有 2 个问题未决定”。默认阻止生成，用户可以选择“在回复中说明暂时无法确认”后继续。

### 9.5 逐项覆盖检查

回复生成结果必须返回：

- 已回答；
- 部分回答；
- 明确延后回答；
- 未回答。

页面在邮件旁显示：

```text
来信问题覆盖
✓ 1. 更新后的交付日期：已回答
✓ 2. 延期原因：已回答
! 3. 补救计划：部分回答，缺少具体负责人
— 4. 赔偿要求：用户尚未确认立场
```

“仍未回答的问题”单独置于结果上方或紧邻主按钮，不放在折叠区。用户编辑正文后，旧覆盖检查标记为过期；可由用户主动重新检查。

### 9.6 长邮件、邮件线程和签名

- 首发支持纯文本粘贴，不支持附件和文件上传。
- 输入达到长度上限时停止 AI 调用，提示用户只保留相关线程或分段处理。
- 对邮件线程优先识别最新一封正文，同时保留前文中被最新邮件引用的未解决事项。
- 不把整段历史中的重复内容统计为多个问题。
- 谨慎识别 `From / Sent / To / Subject`、引用符号和常见签名分隔符。
- 原签名、免责声明和长邮件页脚不作为对方诉求，但不在解析失败时擅自删除正文。
- 页面显示“检测到邮件线程”并允许用户确认分析范围；首发不提供复杂线程编辑器。

### 9.7 抵御原邮件中的恶意指令

收到的邮件属于不可信业务内容，不是系统指令。实现时必须：

- 用清晰的数据边界包裹原邮件；
- 系统 Prompt 明确要求忽略邮件内试图改变任务、输出格式、安全规则或系统身份的文字；
- 不允许原邮件控制工具、模型参数、签名或导出行为；
- JSON 字段只接受预定义结构和枚举；
- 不执行邮件中的链接、代码、HTML、附件指令或“忽略之前要求”等文本；
- 对疑似 Prompt 注入内容给出普通风险提示，不在结果中复述恶意指令；
- 使用固定对抗样例进行 Prompt 契约测试。

### 9.8 回复流程失败与恢复

- **来信分析失败**：保留原邮件，允许重试；不显示伪造的空分析。
- **部分字段缺失**：显示可用分析，并将缺失项标记为“需要人工确认”。
- **回复生成失败**：保留原邮件分析和所有用户立场，只重试生成步骤。
- **格式修复失败**：若能安全识别邮件则显示正文，覆盖分析标记不可用；否则显示安全错误。
- **页面重跑**：不自动再次调用 AI。
- **原邮件修改**：立即使原分析、立场映射和回复结果失效，要求重新分析。

## 10. 技术架构建议

### 10.1 比较过的方案

#### 方案 A：继续单文件扩展

优点是改动最少；缺点是 `app.py` 会快速超过 2000 行，四个工作流之间的状态和控件重复难以测试。不可取。

#### 方案 B：按技术层一次性全面重构

立即建立完整的 `services/`、`models/`、`data/`、`ui/` 和路由框架。边界清晰，但一次性迁移风险高，容易在尚未验证回复流程前产生大量形式化代码。

#### 方案 C：按工作流渐进拆分（推荐）

保持 Streamlit 单应用和当前 DeepSeek 连接方式，先建立最少的共享模型、状态管理和页面边界，再逐阶段迁移。每个阶段都保留 V1.0 可运行回退路径，避免“大爆炸”重写。

### 10.3 模块边界

- `ui/` 只收集输入、调用工作流服务、显示状态，不组装 Prompt。
- `services/` 不导入 Streamlit，不直接读 `st.session_state` 或 `st.secrets`。
- `models/` 使用无副作用 dataclass，作为 UI、服务和测试之间的契约。
- `data/` 只保存无密钥、无用户数据的静态场景定义。
- `prompts/` 只生成消息，不执行网络请求。
- `ai_client.py` 只处理 DeepSeek 请求、用量、错误和格式修复，不知道具体页面。
- 邮件签名继续由 Python 本地逻辑添加，AI 不生成发件人身份。
- 导出只在内存中构建下载内容，不写服务器文件。

## 13. Session State 设计

### 13.1 原则

- 所有 key 使用工作流前缀：`compose__`、`reply__`、`improve__`、`preflight__`、`shared__`、`system__`。
- 页面组件只绑定标量 key；服务调用前组装 dataclass 输入快照。
- 每个工作流独立维护输入、结果、错误和请求状态。
- 共享发件人信息只保留一份。
- 不使用一个全局 `request_in_progress` 表达所有任务。
- 页面重跑不触发 AI；只有按钮事件触发。
- 分析结果绑定源输入摘要，源邮件修改后必须使旧分析和旧高风险确认失效。
- 编辑后的输出不得被无关重跑覆盖。
- “清空当前任务”只清除当前工作流，不影响共享签名和其他工作流。

### 13.2 推荐状态分区

| 前缀 | 示例 |
| --- | --- |
| `system__` | 当前页面、服务状态、最近耗时、Token |
| `shared__` | 发件人信息、默认地区 |
| `compose__` | 场景、动态字段、语气、结果、确认摘要 |
| `reply__` | 原邮件、原文摘要、分析、逐项立场、回复结果 |
| `improve__` | 原草稿、目标语气、结果 |
| `preflight__` | 待检查邮件、本地检查、AI 报告 |

### 13.3 状态管理接口

在 `ui/state.py` 提供：

- `initialize_state()`；
- `set_active_page(page)`；
- `invalidate_if_source_changed(workflow, digest)`；
- `begin_request(workflow, operation)`；
- `finish_request(workflow, result)`；
- `fail_request(workflow, safe_error)`；
- `reset_workflow(workflow)`。

接口负责键名和状态迁移，页面不直接散布数十个状态赋值。不得把 API Key、访问码或完整异常存入 Session State。

## 15. 测试策略

### 15.1 测试分层

1. **单元测试**：数据模型、场景校验、风险、本地化、签名、导出和解析。
2. **契约测试**：每类 AI JSON 的有效、缺失字段、代码块、破损 JSON、一次修复和降级。
3. **工作流测试**：状态迁移、输入摘要失效、请求锁、用户立场和结果保留。
4. **AppTest**：四入口导航、表单校验、高风险门槛、分析到回复的多步骤交互。
5. **视觉检查**：普通笔记本和 390px 移动端，检查溢出、层级和主按钮可见性。
6. **安全静态检查**：Secrets 跟踪、疑似密钥、本地绝对路径、用户内容写盘和日志输出。

### 15.2 AI 测试规则

- 自动化测试统一注入假客户端；

- 对每次按钮操作断言确切调用次数；
- 修复性请求最多一次，并计入调用次数和 Token。

### 15.3 质量回归样例

建立小型、无敏感信息的固定样例集，覆盖：

- 事实完整和事实不足；

## 16. 风险和限制

### 16.1 最大的三个技术风险

1. **多步骤回复流程的状态一致性**  
   原邮件、AI 分析、用户逐项立场和最终回复必须绑定同一内容摘要。任何上游修改都应使下游结果失效，否则可能回复错误事实。

2. **不同任务的 AI 结构化输出可靠性**  
   V2.0 至少有四类返回结构。若继续用一个宽松 JSON 模型，会产生静默缺字段。必须使用独立解析器、明确枚举和安全降级。

3. **在不破坏 V1.0 的前提下拆分 1459 行页面**  
   一次性重写会同时影响访问门禁、复制、签名、状态和移动端。应渐进迁移、保留兼容入口，并以回归测试控制风险。

### 16.2 产品限制

- AI 可能遗漏原邮件隐含诉求；
- 场景表单无法覆盖所有企业流程；
- 本地风险规则可能误报或漏报；
- 本地化提示不能替代对方正式资料；
- `.eml` 导出不等于邮箱集成或自动发送；
- 无账户和数据库意味着刷新或 Session 结束后无法恢复任务；
- Streamlit Session State 只适合当前阶段的单会话工作流。

## 18. 首批场景库设计

首批场景以高频、事实字段清楚、法律风险相对可控为原则。以下 14 个场景覆盖采购、项目工程、行政和管理工作。

### 18.1 采购与供应商

#### SCN-PROC-001：催报价 / Request a Quotation Update

- **适用人员**：采购人员、项目工程师。
- **必填字段**：供应商或联系人、询价事项、原请求日期、希望收到报价的期限。
- **可选字段**：询价编号、项目名称、影响、所需报价明细。
- **默认语气**：正式。
- **必须检查的风险**：内部预算、供应商底价、未经授权的价格承诺、期限。
- **预期输出**：简洁说明询价背景，要求确认报价状态和提交时间。
- **简短示例**：上周已发送泵组询价，请供应商在周四前提交正式报价及交期。

#### SCN-PROC-002：催交期 / Follow Up on Delivery

- **适用人员**：采购人员、项目经理、物流协调人员。
- **必填字段**：订单或设备、原定交期、当前状态、要求对方采取的行动、新回复期限。
- **可选字段**：PO 编号、延迟影响、期望的新交付计划。
- **默认语气**：明确强硬。
- **必须检查的风险**：确定性承诺、客户机密、项目编号、责任指认。
- **预期输出**：明确指出延期、影响、所需更新和回复期限，不使用威胁措辞。
- **简短示例**：原定 8 月 10 日交付，目前未收到发运通知，请周五前确认状态和恢复计划。

#### SCN-PROC-003：要求更新计划 / Request an Updated Plan

- **适用人员**：采购人员、计划工程师、项目经理。
- **必填字段**：需要更新的计划、当前版本或原约定、需要更新的内容、提交期限。
- **可选字段**：延迟影响、计划格式、相关里程碑。
- **默认语气**：正式。
- **必须检查的风险**：未公开进度、确定日期、责任和影响描述。
- **预期输出**：列出计划必须包含的信息，并明确提交要求。
- **简短示例**：请更新制造和检验计划，显示关键里程碑，并于本周五提交。

#### SCN-PROC-004：要求供应商解释延期 / Request a Delay Explanation

- **适用人员**：采购人员、项目经理、质量人员。
- **必填字段**：延期事项、原定计划、已知当前状态、需要解释的问题、回复期限。
- **可选字段**：对项目影响、已发生的沟通、希望提供的纠正措施。
- **默认语气**：明确强硬。
- **必须检查的风险**：无证据指责、违约责任、赔偿、接受责任。
- **预期输出**：要求事实说明、根本原因和恢复措施，同时避免提前作法律结论。
- **简短示例**：检验日期已两次推迟，请说明原因并提交恢复措施和新计划。

#### SCN-PROC-005：PO 确认 / Confirm a Purchase Order

- **适用人员**：采购人员、订单管理员。
- **必填字段**：PO 编号、需要对方确认的事项、确认期限。
- **可选字段**：数量、交期、交货地点、付款条款引用、附件说明。
- **默认语气**：正式。
- **必须检查的风险**：价格、付款条款、合同承诺、账号信息和附件。
- **预期输出**：要求供应商确认收到 PO，并明确列出需确认的关键条款。
- **简短示例**：请确认收到 PO-2026-018，并确认数量、交期和交货地址。

### 18.2 项目与工程

#### SCN-PROJ-001：项目进展汇报 / Project Progress Update

- **适用人员**：项目工程师、项目经理、部门经理。
- **必填字段**：汇报周期、已完成事项、当前状态、下一步。
- **可选字段**：阻塞、影响、需要管理层决定的事项、里程碑。
- **默认语气**：高管简洁。
- **必须检查的风险**：未公开进展、确定性承诺、内部责任和客户机密。
- **预期输出**：用结论优先的结构说明进展、阻塞、影响和下一步。
- **简短示例**：本周完成技术澄清，两份文件仍待客户审批，可能影响采购启动。

#### SCN-PROJ-002：风险升级 / Escalate a Project Risk

- **适用人员**：项目经理、部门经理、项目工程师。
- **必填字段**：风险事实、当前影响、已采取措施、需要的决定或支持。
- **可选字段**：责任方、时间窗口、替代方案、附件。
- **默认语气**：正式。
- **必须检查的风险**：责任认定、法律结论、未授权承诺、内部机密。
- **预期输出**：区分事实、潜在影响、已采取措施和待决策事项。
- **简短示例**：客户审批持续延迟，可能影响采购窗口，请管理层确认是否调整里程碑。

#### SCN-PROJ-003：文件审批催办 / Follow Up on Document Approval

- **适用人员**：文控、项目工程师、项目经理。
- **必填字段**：文件名称或编号、提交日期、当前状态、要求的行动、回复期限。
- **可选字段**：版本号、审批影响、附件或链接说明。
- **默认语气**：正式。
- **必须检查的风险**：文件编号准确性、截止日期、机密文件信息。
- **预期输出**：清楚引用文件和提交记录，要求审批或状态更新。
- **简短示例**：文件 DOC-104 Rev.2 已于周一提交，请周四前完成审批或提供意见。

#### SCN-PROJ-004：技术澄清请求 / Request Technical Clarification

- **适用人员**：项目工程师、设计工程师、采购技术人员。
- **必填字段**：技术主题、已知条件、具体问题、需要回复的期限。
- **可选字段**：图纸或规范编号、可选方案、附件说明、影响。
- **默认语气**：正式。
- **必须检查的风险**：技术事实被改写、编号、未经确认的设计结论、附件。
- **预期输出**：保留技术术语，逐项列出需要澄清的问题。
- **简短示例**：请确认规范第 4.2 条适用的材料等级，并说明是否接受替代方案 B。

#### SCN-PROJ-005：会议行动项确认 / Confirm Meeting Action Items

- **适用人员**：项目经理、项目工程师、会议协调人员。
- **必填字段**：会议名称或日期、行动项、责任人或责任方、截止日期。
- **可选字段**：参会人、争议事项、下次会议时间、附件。
- **默认语气**：正式。
- **必须检查的风险**：错误分配责任、日期、承诺和遗漏行动项。
- **预期输出**：按清单确认行动项、负责人和期限，并请对方纠正不一致之处。
- **简短示例**：确认今日会议的三项行动，请各负责人核对并在有异议时于明天反馈。

### 18.3 行政与管理

#### SCN-ADMIN-001：会议邀请 / Meeting Invitation

- **适用人员**：行政人员、HR、项目人员、经理。
- **必填字段**：会议目的、日期、时间、时区、参会对象。
- **可选字段**：地点或会议链接、议程、所需准备、确认期限。
- **默认语气**：正式。
- **必须检查的风险**：日期、时区、地点、链接、参会范围和附件。
- **预期输出**：完整会议邀请，清楚显示目的、时间、议程和确认要求。
- **简短示例**：邀请客户团队参加下周二 10:00（新加坡时间）的项目协调会议。

#### SCN-ADMIN-002：请求审批 / Request Approval

- **适用人员**：行政人员、项目经理、部门经理、HR。
- **必填字段**：需要审批的事项、原因、期望审批结果、需要决定的期限。
- **可选字段**：金额、预算来源、附件、备选方案、影响。
- **默认语气**：正式。
- **必须检查的风险**：金额、预算、权限、付款承诺、敏感附件。
- **预期输出**：清楚说明背景、审批事项、影响和所需决定。
- **简短示例**：申请批准调整下周客户会议场地，并请周三前确认。

#### SCN-ADMIN-003：通知安排变更 / Notify an Arrangement Change

- **适用人员**：行政人员、项目协调人员、HR。
- **必填字段**：原安排、新安排、变更生效时间、需要对方采取的行动。
- **可选字段**：变更原因、影响、联系人、附件。
- **默认语气**：友好。
- **必须检查的风险**：新旧日期混淆、时区、地址、已确认承诺。
- **预期输出**：先说明变化，再给出新安排和确认要求。
- **简短示例**：原定周四的客户会议改至周五 14:00，请确认参会安排。

#### SCN-ADMIN-004：客户来访确认 / Confirm a Client Visit

- **适用人员**：行政人员、销售支持、项目经理。
- **必填字段**：客户或团队、来访日期、地点、访问目的、需要对方确认的事项。
- **可选字段**：人员名单、交通、住宿、门禁资料、联系人、议程。
- **默认语气**：友好。
- **必须检查的风险**：个人信息、证件信息、地址、行程、附件和隐私。
- **预期输出**：确认来访安排和待提供信息，不要求用户提交不必要的身份资料。
- **简短示例**：确认客户团队 8 月 18 日来访，请对方提供参会名单和到达时间。

### 18.4 首页首批展示

首页直接展示：

1. 回复收到的邮件；
2. 催供应商（进入后选择催报价、催交期、计划更新或延期解释）；
3. 会议邀请；
4. 项目进展汇报；
5. 请求审批；
6. 确认交期或计划；
7. 优化已有草稿；
8. 发送前检查。

其中前六项属于任务或场景入口，后两项属于处理现有内容的工具入口。

### 18.5 “更多场景”

以下场景放入分类列表：

- PO 确认；
- 风险升级；
- 文件审批催办；
- 技术澄清请求；
- 会议行动项确认；
- 通知安排变更；
- 客户来访确认。

### 18.6 不适合首发的场景

- 合同索赔和正式违约通知；
- 赔偿、责任接受或权利放弃；
- 录用、解雇、纪律处分和薪酬谈判；
- 银行账户变更、付款指令和收款确认；
- 正式法律意见；
- 报价批准、价格授权和最终合同条款谈判；
- 包含大量附件才能理解的技术或法律邮件。

这些场景涉及更高授权、法律、安全或附件依赖，不能只靠通用场景 Prompt 安全上线。

### 18.7 场景扩展机制

场景应由 `EmailScenario` 和 `ScenarioField` 数据定义驱动，而不是每个场景编写一个新页面。新增场景时：

1. 添加唯一场景 ID 和显示文案；
2. 组合已支持的字段类型；
3. 指定必填、可选、默认语气和风险策略；
4. 引用经过审核的 Prompt 策略标识；
5. 增加场景完整性和 Prompt 契约测试；
6. 通用场景渲染器自动生成表单。

只有出现新的交互类型或业务规则时才修改页面代码。

## 19. V2.0 产品成功标准

### 19.1 可验证指标

首轮指标用于 5 至 10 名受邀测试用户，不作为大规模统计结论。

| 目标 | 测量方式 | 首轮建议标准 |
| --- | --- | --- |
| 不写完整草稿也能完成邮件 | 观察用户是否仅填写场景字段完成任务 | 至少 8/10 个新邮件任务无需用户先写完整草稿 |
| 普通新邮件 60 秒内完成 | 从选择场景到获得首个可审核结果计时，包含正常 API 等待 | 至少 70% 的普通任务在 60 秒内完成；中位数不超过 60 秒 |
| 正确识别来信主要问题 | 与人工预先标注的问题清单对比 | 主要问题召回率至少 90%，且关键期限、金额不得错误改写 |
| 回复覆盖主要问题 | 对生成回复逐项人工审核 | 至少 90% 已确认事项被完整覆盖；不得擅自承诺 |
| 减少 Prompt 编写 | 记录用户是否需要输入开放式指令 | 至少 80% 的测试任务不需要用户编写自定义 Prompt |
| 减少大量重写 | 用户标记“直接可用 / 小改 / 大改 / 不可用” | 至少 70% 结果为“直接可用”或“小改”；“大改或不可用”低于 20% |
| 愿意再次使用 | 任务结束后 5 分量表 | 至少 7/10 用户选择 4 或 5 分 |
| 不再被认为只是翻译 | 询问用户如何描述产品 | 至少 8/10 用户能提到场景、回复分析、检查或遗漏提示之一 |
| 比通用聊天 AI 更方便 | 同一用户完成一次对照任务后评分 | 至少 7/10 用户认为 Leon AI 更省步骤或更容易完成 |

安全质量是发布门槛，不只看平均指标：

- 测试中不得出现系统自动发送邮件；
- 不得把未选择的回复立场写成接受；
- 不得泄露 API Key 或访问码；
- 修改原邮件后不得继续使用旧分析；
- 自动化测试不得调用真实 DeepSeek。

### 19.2 5 至 10 人测试方法

建议招募：

- 2 名项目或工程人员；
- 2 名采购或供应链人员；
- 1 至 2 名行政或 HR；
- 1 至 2 名项目经理或部门经理；
- 至少 2 名不常使用 Prompt 的用户。

每人完成三个任务：

1. 一个场景化新邮件；
2. 一个包含至少三个问题的回复邮件；
3. 一个草稿优化或发送前检查。

对其中一个任务，让用户先使用自己常用的通用聊天 AI，再使用 Leon AI，记录完成时间、输入字数、操作步骤、遗漏和修改量。测试材料使用虚构或脱敏内容。

### 19.3 反馈问题

1. 你是否需要先想好 Prompt 才能开始？
2. 哪些字段让你觉得多余，哪些信息系统没有询问？
3. 你是否理解系统为什么追问这些事实？
4. 来信分析是否找出了你认为必须回复的问题？
5. 系统有没有把你未确认的内容写成承诺？
6. 最终邮件需要怎样修改才能发送？
7. 哪一步最慢或最令人困惑？
8. 你会如何向同事描述这个工具？
9. 与直接使用豆包、ChatGPT 或 DeepSeek 相比，哪种方式更方便，为什么？
10. 下一次遇到类似邮件，你是否愿意再次使用？

## 20. V2.0 首发边界与后续规划

### 20.1 V2.0 首发包含

- AI商务邮件工作台首页和四个核心入口；
- 14 个首批场景的数据定义；
- 场景化写新邮件；
- 来信分析、逐项立场和回复覆盖检查；
- 草稿优化；
- 独立发送前检查；
- 本地敏感信息和本地化称谓提示；
- 发件人动态签名；
- 一键复制主题；
- 一键复制正文；
- 一键复制完整邮件；
- 打开默认邮件客户端并预填主题和正文；
- 下载基础 `.eml` 草稿；
- AI 服务状态、耗时和可用 Token；
- 测试访问码。

“打开默认邮件客户端”只构造用户主动点击的 `mailto:` 草稿，不代表邮件已发送。需要处理 URL 长度、换行和特殊字符；内容过长时应提示使用复制或 `.eml`。

`.eml` 仅在内存中生成并由用户下载，不写服务器目录，不包含附件，不自动导入邮箱。

### 20.2 V2.0 明确不做

- 自动发送邮件；
- Outlook OAuth；
- Microsoft Graph；
- Gmail 连接；
- 用户注册；
- 支付和订阅；
- 数据库；
- 历史记录；
- 企业知识库；
- 附件解析；
- Word 或 PDF 上传；
- 团队协作；
- 多模型切换。

### 20.3 V2.1 候选

- 根据首轮数据调整首页高频场景；
- 扩展低风险场景库；
- 更完善的 `.eml` 兼容性；
- 任务内的可选邮件版本对比；
- 在不保存邮件正文的前提下改进本地偏好设置；
- 更系统的 Prompt 质量回归样例。

### 20.4 更后续版本

- Outlook 或 Gmail 正式连接；
- 附件和文件解析；
- 账号、历史记录和跨设备恢复；
- 团队模板和企业知识库；
- 权限、审计和企业管理；
- 使用额度、支付和订阅；
- 经验证后的多模型策略。

以上功能需要新的隐私、安全、授权、数据保存和运维设计，不能作为 V2.0 首发的隐含范围。

## 21. 审计结论

V1.0 已具备可复用的 DeepSeek 客户端、错误处理、JSON 修复、签名、内容风险、本地化、访问门禁和 Streamlit 测试基础。V2.0 不需要更换框架或重写全部服务。

推荐采用“按工作流渐进拆分”的方案：先建立首页、导航和状态边界，再用场景化新邮件验证目录和模型设计，之后实施技术风险最高的智能回复，最后增加发送前检查和内存导出。这样可以让每个阶段保持可运行、可测试并可回滚。
